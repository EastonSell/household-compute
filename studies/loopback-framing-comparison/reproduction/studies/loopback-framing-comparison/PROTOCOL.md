## Question and scope

Does the exact previously accepted finite-validation candidate reduce complete synthetic frame delivery-and-acknowledgement latency when both sending and receiving processes use that codec, compared with the unchanged baseline? This tests a two-ended treatment. It does not identify whether sending or receiving is responsible. It is not a mesh implementation, a throughput test, real-device evidence, cross-host networking, inference, or model-quality evaluation. One host, one persistent IPv4 TCP connection and one outstanding frame are used. There is no injected delay, concurrency sweep, tuning, model loading or external endpoint.

## Fixed schedules and denominator

Canary: one fresh driver invocation, one receiver, eight untimed one-exchange commands in case-major A/B order, then orderly close and child reap. No warmups or latency summaries. Every canary exchange must validate exactly. Its observations may be used only for admission, never for selecting sample counts or a favorable protocol.

Measurement: exactly run-001 then run-002, fresh driver and one fresh receiver each. Each run first performs two untimed exchanges per case/variant in case-major A/B order (16 warmup exchanges). Then ten blocks. The four cases stay in their listed order in each block. Case fixed index c uses AB when (block+c)%2==0, otherwise BA. Each case has five AB and five BA pairs. Each variant batch has ten sequential acknowledged exchanges. Therefore each run has exactly 80 measured rows, 40 adjacent pairs and 800 measured exchanges plus 16 warmups. Across both runs: 160 rows, 80 pairs and 1,600 measured exchanges plus 32 warmups. Canary eight exchanges are a separate denominator. Nothing is retried, replaced, retimed, discarded as an outlier or adaptively extended.

A failure stops the current run and prevents the next. Retain partial journal, receiver evidence and any terminal failure. A source change after any socket canary requires a newly labeled protocol/version, preservation of the prior canary, and renewed independent admission. A source change after any performance observation similarly terminates this protocol version. Never manufacture a successful pair by replacing a failed run.

## Exact timed boundary

A fixed 8-byte command and 8-byte READY acknowledgement select the next prescheduled case, variant and iteration count outside timing. No payload or algorithm is selected by arbitrary network input. The driver records perf_counter_ns immediately before the exchange loop. Each iteration enters a wrapper that creates its absolute deadline and a fresh byte ledger, then calls codec.write_frame. For each iteration that call validates and packs the preconstructed Frame and sends its bytes through the deadline adapter. The receiver creates a fresh matching Decoder, incrementally reads/decodes/validates the complete frame, compares exact Frame type/header/payload against its expected fixture, and only then sends a fixed 16-byte ACK containing magic, command index, iteration index and received frame length. The driver fully receives and validates that ACK before continuing. Each successful exchange increments an in-flight completion counter after ACK validation; perf_counter_ns is sampled immediately after the loop, including the final increment. The positive wall interval divided by ten is the batch mean latency per complete delivery-and-ACK operation.

Included: sender validation/packing/allocation, real kernel loopback stream I/O, receiver parsing/copies/validation and equality check, cross-process scheduling, ACK construction/transmission/validation, adapter deadline checks and Python loop overhead. Excluded: process/connection/fixture setup, command/READY control, warmups, journal serialization/writes, final shutdown and cleanup. Exact frame/ACK byte-counter deltas are checked outside timing. Application byte counts are not IP/TCP wire traffic. No CPU-time, allocation, RSS, energy, standalone bandwidth or request-throughput metric is inferred. Operational elapsed time for resource control is not a second performance endpoint.

Each transaction has a fixed 2-second absolute monotonic deadline shared by frame send and ACK receive, bounded by the run's work deadline. Receiver receive/ACK also uses a fixed 2-second deadline after its READY send, bounded by the same work deadline. These are transport timeouts, not latency censoring replacements. Timeout fails the entire run. Per-block variant order changes only as prescribed.

## Adapter, ownership and bounds

Only literal 127.0.0.1 is bind/connect eligible; port zero selects an ephemeral port. Listener backlog 1; one accepted peer, validated loopback and a fresh 32-byte correlation nonce before commands. Driver creates the listener, passes only its FD to the one trusted local Python receiver via Popen(pass_fds), immediately closes its listener copy, and connects. Receiver closes listener immediately after its sole accept. No socketpair, DNS, public address, household device, real model, installation, paid resource or credential/configuration operation is used.

All sockets are nonblocking. select waits use min(remaining absolute deadline, 50 ms) and recheck clock/deadline before and after wait and syscall. Interrupted/would-block retries remain within the same deadline; zero/EOF, wrong peer, short/overlong contract, backward/nonfinite clock and deadline expiry are terminal. No timeout resets on partial progress. Signal-driven Python exceptions propagate to finally cleanup; no background I/O threads or process groups exist.

The driver is the sole Popen owner/reaper. It stores the actual Popen object, never accepts an external PID, never uses name lookup or os.kill directly, and never launches descendants. Receiver is trusted, single-process standard-library code. Cleanup closes the driver socket, waits briefly for normal exit, then calls terminate only if that same owned child remains live, waits, then kill only if still live, and waits again. Retain PID, final return code, whether termination/escalation was requested, and reaped=true only when wait confirms. Never signal a reaped child. An exception during cleanup is retained as failure; sending a signal alone is not cleanup success. PID is a local lifecycle identifier, not proof of machine identity.

The operational run budget is 90 seconds from before source checks/fixtures through cleanup and the final integrity/elapsed gate. Final terminal-journal and result-file writes are bounded in bytes but occur after that last timing gate; their completion is not included in retained operational elapsed time. Work must end before 85 seconds. Startup/connect/nonce deadline is min(start+10, work deadline). Child receives the same absolute work deadline and exits on any exception. Cleanup reserves at most one second normal wait, one second after terminate and one after kill, each bounded by the remaining total deadline. Parent killed abruptly is not guaranteed to write evidence; child has its own absolute deadline and bounded I/O, but this is not hostile-process containment or a kernel hard resource cap. OS scheduling, file writes and bounded pure-Python codec work can overshoot. An external supervisor must not be described as safe group cleanup; the collection operator should retain any external intervention as failure.

The fixed ten-block, ten-exchange batch count is deliberately modest: paired order is balanced, each condition has ten batch observations, and transfer volume remains under 80 MB per run without tuning against observed data. This is a descriptive demonstration, not a power-based population design.

At most two Python processes, one listener (closed after accept), one connected socket per process, one in-flight frame, a 196,676-byte maximum frame and 16-byte ACK. Fixtures are below 1 MiB payload data per process before copies/interpreter overhead; no RSS cap is claimed. Actual one-way payload frame bytes per measured run are 76,698,400; ACK bytes are 12,800. Warmups add 1,533,968 frame bytes and 256 ACK bytes. Canary adds 766,984 frame bytes and 128 ACK bytes. Control, nonce and finish bytes are reported separately. No payload bytes are retained in journals.

Output is a new exclusive directory; refuse existing paths. Parent journal, parent result, receiver result each cap 1 MiB; terminal reserve 4 KiB. Journals flush after complete rows outside timers, not fsync. File or disk failures may leave partial evidence. Cleanup must occur even if journaling fails. Both processes retain actual positive send/recv counts before checking the post-syscall deadline, snapshot partial totals on ordinary failures, retain preceding complete commands, and retain the active command stage/index, completed-exchange count and partial transfer counts. Cleanup exceptions carry the owned-child record, including attempted signals and unconfirmed reap. Socket-close errors do not skip other closes or child cleanup. A terminal-journal error still permits an attempted failed result write. Baseline inventory and frozen sources are checked before launch and after cleanup. All earlier tracked files are inventoried byte-for-byte; no existing package is changed.
